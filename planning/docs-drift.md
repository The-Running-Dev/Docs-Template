# docs-template — stale version claims, undocumented components, uncategorized guides

**Status:** Open
**Severity:** low — nothing breaks, but readers are misled
**Labels:** `documentation`
**Found:** 2026-07-27 audit, against `main` at `3965669` (#47)

Three documentation gaps, groupable into one pass.

## Problem 1 — three docs advertise Docusaurus 3.8.1; the dependency is 3.10.1

### Evidence

`package.json:83` pins `"@docusaurus/core": "3.10.1"`. Three prose locations
still say 3.8.1:

| File | Line | Text |
| --- | --- | --- |
| `README.md` | 9 | "🚀 **Modern Docusaurus 3.8.1** with TypeScript support" |
| `docs/index.md` | 13 | "🚀 **Modern Docusaurus 3.8.1** with full TypeScript support" |
| `docs/getting-started/features.md` | 9 | "🚀 **Modern Docusaurus 3.8.1** - Latest version with TypeScript support" |

Already flagged as `TODO.md` P1.3; this pins the exact occurrences.

### Required fix

Preferred: stop hardcoding the patch version in prose — "Modern Docusaurus 3"
in all three places, so the claim cannot rot again. If the number should stay,
update all three in one commit and add them to the release checklist (or extend
the doc gate's terminology rules to catch version strings), so the next bump
cannot miss one.

Check first whether `docs/index.md` is regenerated by
`ConvertTo-DocumentationHomepage.ps1` from `README.md` — if so, fix the source,
not the artifact.

## Problem 2 — four components have no documentation

### Evidence

- **`DataProvider`** and **`DebugInfo`** appear nowhere in `docs/` — no
  core-systems page, no mention in `key-components.md` — despite both having
  test suites, so they are maintained code rather than scraps.
- **`ReaderMode`** and **`TextSizeSwitcher`** have live demo pages
  (`src/pages/demos/reader-mode.tsx`, `src/pages/demos/text-size-switcher.tsx`)
  and navbar toggles, but only a one-line mention in
  `docs/configuration/key-components.md` — while sibling navbar toggles get full
  pages (`docs/core-systems/theme-system.md`,
  `docs/core-systems/version-display-system.md`).

A reader working through the core-systems section concludes the reader-mode and
text-size features do not exist, or are not supported.

### Required fix

1. Write `docs/core-systems/reader-mode.md` and
   `docs/core-systems/text-size-switcher.md`, modeled on `theme-system.md`:
   what the toggle does, where it persists state (localStorage key), how a
   consumer enables or disables it, and a link to the demo page.
2. For `DataProvider` and `DebugInfo`, first decide whether they are public
   surface or internal plumbing. Public → document them the same way. Internal
   → say so once, in a short "internal components" note in
   `docs/core-systems/components-system.md`, so their absence reads as a
   decision rather than an omission.
3. Cross-link each new page from the demos and from `key-components.md`.

## Problem 3 — `docs/guides/` has no category metadata

### Evidence

Every docs section (`getting-started/`, `configuration/`, `core-systems/`,
`advanced/`, `pull-requests/`) carries a `_category_.json` — except
`docs/guides/`, which holds four files (`api-specs.md`,
`admin-projects-interface-specs.md`, `unified-projects-auth-specs.md`,
`projects-manager.md`) with none. Its sidebar label, position, and collapse
behaviour are whatever the autogenerated defaults produce.

Three of the four are *specification* documents for the API and admin work, not
how-to guides — which raises the prior question of whether they belong in
published docs at all, given `TODO.md` P2 wants the API out of Phase 1
documentation and navigation paths.

### Required fix

Decide placement first; it is cheapest now.

- **If they stay published**, add `docs/guides/_category_.json` matching the
  siblings' shape:

  ```json
  {
    "label": "Guides",
    "position": 6,
    "collapsed": true,
    "link": {
      "type": "generated-index",
      "description": "Specifications and working guides for the projects and admin systems."
    }
  }
  ```

- **If the API specs move to Phase 2** per `TODO.md` P2, relocate the three spec
  files out of `docs/` — to `planning/` or the API package — leaving
  `projects-manager.md` in a properly categorized section.

## Acceptance criteria

- `grep -rn "3\.8\.1" README.md docs/` returns nothing.
- Every navbar-visible feature has a core-systems page.
- Every component under `src/components/` is either documented or explicitly
  listed as internal.
- No docs section relies on autogenerated category defaults.
